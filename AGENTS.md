# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Two services: `backend/` (FastAPI + SQLModel/Postgres) and `frontend/` (Next.js App Router). See the root `README.md` for how to run both locally.
- There is no user auth anywhere in this product. Spotify access is server-side only, via the Client Credentials flow (app-level token, no login) in `backend/app/spotify_client.py`. This was a deliberate captain decision: Spotify's Development Mode caps a new app at 5 logged-in users with no realistic path to more for a solo project, so personalized login was dropped entirely.
- Spotify's `audio-features`/`audio-analysis` endpoints are gone for any app registered after 2024-11-27. There is no first-party energy/valence/danceability data available, and `preview_url` is frequently null/unpredictable per track - real-world testing across several major albums found zero available preview clips, so treat preview availability as the exception, not the norm.
- The per-track vibe pipeline (`backend/app/vibe_service.py`) tries three sources in order: cache -> ReccoBeats (`backend/app/reccobeats_client.py`, keyed by Spotify track ID, no audio needed) -> preview+librosa (`backend/app/vibe_analysis.py`) -> `None`. ReccoBeats is primary precisely because preview clips are now rarely available; librosa remains only as a fallback for tracks ReccoBeats has no data for. See `reccobeats_client.py`'s docstring for the confirmed API contract (base URL, no-auth-required, field mapping) and `vibe_analysis.py`'s docstring for why Essentia's pretrained mood classifiers weren't used for the fallback (no model weights ship with the pip package; running them needs a separate runtime download this repo doesn't vendor). Beyond the original energy/brightness(valence)/tempo, ReccoBeats-sourced rows also carry danceability/acousticness/instrumentalness/speechiness/loudness/key/mode (used by the guessing game's hint reveal - see below); the librosa fallback has no equivalent for these, so they're `None` on `source == "librosa_fallback"` rows. Results are cached in Postgres by Spotify track ID (`TrackVibe` model, whose `source` column traces which pipeline produced a row) so a track is only ever computed once, even across different albums/playlists/rounds. A track with no data from either source gets `vibe: null` rather than failing the request.
- Backend tests never call the real Spotify or ReccoBeats APIs - they mock `httpx` calls with `respx` (see `backend/tests/`). Keep it that way; live credentials should never be required to run the test suite. Vibe-pipeline tests likewise mock `get_track_vibe`/`download_preview_clip`/`analyze_audio` rather than hitting the network; `backend/tests/fixtures/tiny_clip.wav` is a tiny checked-in fixture for the one test that runs real librosa analysis.
- The product is an artist album-guessing game (not a paste-a-link lookup tool - that mode was fully removed). `backend/app/game_service.py` orchestrates it server-side: resolves an artist (by name search or by exact Spotify ID, the latter used by the frontend's autocomplete to avoid same-name-artist ambiguity), picks a secret target album (rerolling on sparse vibe data), and holds all round state - including the target's identity, track names, and the cumulative list of wrong-guessed (eliminated) album IDs - in the `GameRound` table (`backend/app/models.py`) until a round is solved or given up. Elimination state is server-authoritative and returned in full on every guess response (`GuessResponse.eliminated_album_ids`); the frontend renders from that list rather than accumulating its own, precisely because a previous frontend-only-tracking design had a reported bug there. The `/api/game/rounds*` and `/api/game/artists` endpoints in `backend/app/main.py` are the only access path; no in-progress-round response may ever include the target's identity or a track name - see the tests in `backend/tests/test_game_endpoint.py` that assert this directly against real HTTP responses. Studio-album filtering (`_looks_like_non_studio_edition` / `_dedupe_albums_by_base_name` in `game_service.py`) is a name-pattern heuristic, not a perfect classifier - Spotify's `album_type=album` filter alone still lets live albums, remixes, and deluxe/anniversary/reissue editions through.
- The frontend chart (`frontend/app/GameChart.tsx`) shows one metric's line at a time via a toggle control (not overlaid lines) - a wider, horizontally-scrollable chart with per-point spacing so each point's "Track N" x-axis label and (post-reveal) truncated track title both fit. `frontend/app/MetricGlossary.tsx` always lists every metric's plain-language description from round start, dimming ones not yet unlocked - it's shared between the round and reveal states rather than being reveal-only.
- Spotify's `GET /artists/{id}/albums` endpoint rejects `limit` above 10 with a 400 "Invalid limit" - confirmed live, despite docs suggesting up to 50. `SpotifyClient.get_artist_albums` (`backend/app/spotify_client.py`) pages through the response's `next` link to still collect an artist's full studio catalog. Re-check this ceiling if Spotify ever changes it back.
- `CORSMiddleware` in `backend/app/main.py` lists `allow_methods` explicitly (currently `["GET", "POST"]`) - any new endpoint using a method not in that list will fail purely at the browser's CORS preflight, not at the route itself, which is easy to misdiagnose as a backend bug.
- The backend test suite runs against an in-memory SQLite engine (`DATABASE_URL=sqlite:///:memory:`, set in `backend/tests/conftest.py`), not Postgres. `backend/app/database.py`'s `get_engine()` special-cases in-memory SQLite URLs to use a shared `StaticPool` connection.
- Frontend tests use Vitest + React Testing Library (jsdom), run with `npm test` from `frontend/`. Config is `frontend/vitest.config.mts` / `frontend/vitest.setup.ts`. The setup file polyfills `ResizeObserver` and stubs `HTMLElement` offset dimensions (both needed for Recharts' `ResponsiveContainer` to render in jsdom), and calls RTL's `cleanup()` after each test (not automatic under Vitest). `frontend/app/types.ts` must be kept in sync with `backend/app/schemas.py` by hand - nothing enforces this across the language boundary. `frontend/app/page.test.tsx` mocks `frontend/app/api.ts` (not `fetch` directly) to drive the game's landing/round/reveal states - there's no `user-event` package installed, so tests use RTL's `fireEvent`.
